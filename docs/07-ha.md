# Haute disponibilité — HA Manager

> Pré-requis : quorum fiable + stockage disponible sur les 3 nœuds (réplication en place, doc 04).
> Références : [wiki HA](https://pve.proxmox.com/wiki/High_Availability). **Rien n'est protégé automatiquement** : il faut déclarer chaque VM.

---

## 1. Pré-requis à valider

- [ ] `pvecm status` → Quorate (2 votes sur 3)
- [ ] `pvesm status` → le volume du VM (`tank`) actif sur la cible de bascule
- [ ] `lsmod | grep watchdog` + `/dev/watchdog` présent ; état visible dans `ha-manager status`
- [ ] Réplication `pvesr` du VM **active et récente** vers le nœud de secours (`pvesr status <vmid>`)
- [ ] NTP synchronisé (clocks Corosync) — milliers de mauvais jours viennent d'ici
- [ ] interfaces réseau du VM présentes sur tous les nœuds éligibles (`vmbr2`)
- [ ] pas de passthrough matériel lié à UN nœud (sinon HA impossible)

## 2. Déclarer une ressource HA

```bash
# VM 100 (ex. DNS) — le rendre protégé :
ha-manager add vm:100 --state started

# Containers : préfixe ct: ; état initial stopped :
ha-manager add ct:200 --state stopped

# Vérifier
ha-manager status
#   Name  Sid  State  Node  Watchdog  ...
#   vm:100       started  pve1  armed    ...
```

État de ressource attendu : `started`, nœud = source ; **Watchdog `armed`** (c'est la preuve que le fencing fonctionne).

## 3. Règles d'affinité (PVE ≥ 9 — remplacent les HA groups, dépréciés)

Placer les ressources sur les bons nœuds, et empêcher qu'elles partagent un même nœud.

```bash
# Node-affinity NON-stricte : VMs 100-105 préfèrent pve1/pve2 (soft preference)
ha-manager rules add node-affinity ha-rule-web \
  --resources vm:100 vm:101 vm:102 \
  --nodes pve1 pve2

# Anti-affinité : base de données et noeud critiques jamais sur le même hôte
ha-manager rules add resource-affinity ha-rule-db \
  --resources vm:110 vm:111 \
  --no-state-restriction-on-off 0 \
  --negative
```

Notes (source [HA wiki](https://pve.proxmox.com/wiki/High_Availability) et [page HA/affinité](https://www.anystackarchitect.com/ha-and-multi-site-design-on-proxmox-ve-9-1/)) :

- **Strict** (`--strict`) : ressource confinée à ces nœuds obligatoirement. À réserver aux cas vrais
  (licence/passthrough) : si ces nœuds tombent, la VM ne peut s'ouvrir nulle part.
- En non-strict : si aucun nœud préféré n'est dispo, HA place ailleurs (meilleure robustesse).

## 4. Politiques de redémarrage (bornées)

```bash
# Forcer des bornes (éviter qu'un VM cassé enchaîne les nœuds)
qm set 100 --hastate max_restart=1
qm set 100 --hastate max_relocate=2   # relocalise, ex. sur 2 nœuds

# Contrôler le failback : 0 = ne pas migrer de retour automatiquement
qm set 100 --hastate nofailback=1     # p. ex. pendant une enquête sur un nœud revenu
```

> `max_restart` : nb de tentatives sur le même nœud avant déplacement ;
> `max_relocate` : nb de nœuds tentés. Jamais illimité.

## 5. CRS (scheduling dynamique, PVE 9.1.8+)

Avec HA + rebalancing actif, le cluster répartit automatiquement les ressources pour équilibrer charge :

```bash
pvesh get /cluster/options                    # voir les valeurs crs-*
pvesh set /cluster/options -crs-ha-rebalance-on-start 1
```

> Option `ha-rebalance-on-start` : choisir le meilleur nœud au démarrage d'une ressource arrêtée.
> Le load balancer (si activé) redistribute les ressources HA en fonctionnement normal.
> **Valider en environnement non production avant production** (comportement de migration automatique).

## 6. Checklist de validation complète

- [ ] `ha-manager status` : toutes les ressources `started` sur leur nœud attendu, watchdogs `armed`
- [ ] `journalctl -u pve-ha-crm` et `-u pve-ha-lrm` sans erreur
- [ ] `pvecm status` quorate pendant l'ensemble des opérations
- [ ] un **test de bascule** réalisé en doc 12 (arrêt volontaire du nœud → VM relancée sur la cible, temps mesuré)
- [ ] les règles de réplication collent au placement HA (VM 100 sur pve1 → répliquée vers pve2/3)
